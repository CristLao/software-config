<h1><center>去 AI 味写作</center></h1>

# 先确定读者要得到什么

让读者一次读懂内容, 知道事实, 理解原因或完成操作. 以这个结果判断是否需要修改一句话.  
根据请求判断是写作, 润色还是审校. 默认用中文新写内容, 润色时保留原文语言; 用户另有要求时遵循用户要求.

- 先读原文和相关上下文, 确认读者, 目标, 语气与范围. 信息足够就直接处理, 不例行追问或等待大纲审批.
- 缺少的信息会改变结论或操作时才询问. 可从上下文判断的小问题自行决定, 不虚构缺失事实.
- 用户要求局部修改时控制范围. 保留作者已有的判断, 个性和有用细节, 不把所有文本改成同一种口吻.
- 技术文档先判断文档类型, 再按需读取 [文档写作与审校](references/documentation.md). 普通短文无需套用文档流程.
- 对具体表达拿不准时读取 [中文改写示例](references/examples.md). 需要理解融合来源与取舍时读取 [来源与取舍](references/sources.md).

# 先保事实, 再改表达

- 保留名称, 数值, 日期, 引用, 前提, 例外, 风险, 否定和不确定程度. 不把 "可能" 改成 "一定", 不把相关性改成因果.
- "有研究表明", "业内普遍认为" 等说法要有可追溯来源. 没有来源时标明待核实或删除无法支持的断言, 不编造专家或机构.
- 描述已确认的机制, 行为或结果. "体验更流畅" 要说明哪里改变了; 效果本身缺少依据时删除断言或标注待核实, 不补造数据.
- "从而确保", "充分体现", "进一步彰显" 等尾句要有实际信息和因果依据. 只重复态度或夸大效果时删除.
- 区分已知事实, 作者观点和推测. 删除重复的保留措辞, 保留影响读者判断的限定.
- 不擅自改动代码, 命令, API, 链接目标或直接引文. 发现技术疑点时单独核实, 不靠文字润色掩盖.

# 用具体, 自然的句子表达

| 常见问题 | 处理方式 |
| --- | --- |
| "赋能", "生态", "闭环", "抓手", "范式", "全方位", "无缝", "革命性" | 写出对象, 动作和结果. 属于必要术语时保留并解释含义 |
| "作为...而存在", "扮演着...的角色" | 直接写 "是", "有", "用于" 或具体动作 |
| "不仅仅是 X, 更是 Y", "真正的问题不是 X, 而是 Y" | 直接表达判断; 确有必要区分两个概念时保留具体比较 |
| 为凑气势使用三连词, 排比或宏大范围 | 按实际信息组织, 不强凑三点. "从 X 到 Y" 只用于确有顺序或尺度的范围 |
| 同一概念轮流换近义词 | 固定术语和名称, 避免让读者误以为是不同对象 |
| "显著提升", "极大降低", "几乎为零" | 有证据就给结果和适用条件. 只有程度无依据时删程度词; 效果本身无依据则删除断言或标注待核实. 已确认未测量时才能写 "尚未测量" |
| "轻松", "简单", "只需", "快速上手" | 写明步骤, 前提或成本, 不替读者判断难度 |
| "首先让我们深入探讨", "在当今快速发展的时代" | 从主题, 结论或操作直接开始 |
| "综上所述", "未来可期", "希望这对你有帮助" | 删除重复收尾; 需要结束时写具体结果或下一步 |
| "好问题", "你说得完全正确", "当然可以" | 直接回应内容, 不用恭维或客服式开场 |

这些是检查信号, 不是禁词表. 判断词句是否准确传达信息, 不机械替换.  
英文同样选常用词和直接动词, 如用 `use` 替代无特殊含义的 `utilize` 或 `leverage`; 保留必要术语和专有名称.

- 优先交代谁做什么, 在什么条件下产生什么结果. 主体未知或不重要时可以用被动句.
- 操作步骤直接用动词开头, 如 "打开设置". 面向读者时用 "你" 或省略主语, 少用 "用户需要" 和含混的 "我们".
- 描述当前行为用现在时, 未来计划明确标注. 不把计划写成已实现能力.
- 拆开需要回读的长句, 补全跨句指代. 一个句子围绕一个主要意思, 不硬套英文单词数限制.
- 相关条件, 动作和结果保持连贯. 不为追求短句把完整意思切成连续碎句, 不删成电报体或箭头缩写.
- 段落围绕同一主题自然推进. 转入下一点时接续具体对象, 不用 "了解了以上内容后" 重述上一段.
- 说明功能时写实际行为, 避免逐项朗读规格. 比喻只在帮助理解时使用, 用后回到实际机制; 不用拟人化代替解释.
- 不为制造亲切感添加网络口头禅, 故事, 情绪或个人经历. 原文确有的幽默和鲜明语气可以保留.

# 让结构和格式帮助阅读

- 先给读者当前需要的信息. 长文可以用简短开头说明用途与结果, 短答案直接作答, 不强加摘要和总结.
- 标题说明本节回答什么问题或完成什么动作. 英文标题采用句首大写, 保留产品名称的既定写法.
- 一个章节表达一个完整主题. 段落过长或混入另一主题时拆分, 不把每句话变成小标题.
- 真正并列的内容用无序列表, 有执行顺序的步骤用编号, 对比用表格. 不为凑结构给短文强加三点式列表.
- 避免每项都用加粗标签加冒号重复句意. 标签有助于扫描且后文提供新信息时可以保留.
- 加粗用于界面元素和影响操作的关键信息; 路径, 命令, 标识符用行内代码. 去掉装饰性 emoji 和无作用的强调.
- 破折号, 冒号和括号不承担松散的逻辑连接. 说清因果或拆句, 不用另一种符号替换后保留原问题.
- 链接文字说明目的地, 不用 "点击这里". 术语在目标读者首次需要时解释, 避免为熟悉概念反复下定义.
- 用户和项目已有格式优先. 没有既定规范时, 中文内容使用英文标点和直引号; 代码, 引文和界面原文保持准确.
- 在 `software-config` 仓库内写 Markdown 时, 页标题用 `<h1><center>页面标题</center></h1>`, 正文从 `#` 开始. 普通文本按独立逻辑换行, 段内行尾保留两个空格; 相关命令尽量合并到一个代码块, 可用空行和注释区分.

# 交付前读一遍

按正常语速从头读到尾, 检查是否需要回读, 是否丢失事实或限定, 是否出现新造的空话.  
再检查每段提供了什么新信息. 如果一句话可以原样放进任何项目, 检查它是否缺少当前对象的具体信息.  
技术文档还要确认目标读者能按说明完成任务, 需要的前提与限制没有遗漏.

- 润色: 默认直接给改后正文. 用户要求修改说明时, 再列有实际意义的变化.
- 新写: 交付所需成稿, 不附带过程叙述或自动追加 "写作思路".
- 审校: 按文件分组, 用 `路径:行号 - 问题; 建议改法` 定位. 没有文件或可靠行号时引用短句定位, 不编造行号. 优先指出事实和操作问题, 再处理表达; 修复明显时不长篇解释. 没有问题时直接说明, 不凑问题数量.
- 不声称内容经过真人撰写或保证通过 AI 检测. 成稿是否自然, 以准确, 具体和易读判断.
